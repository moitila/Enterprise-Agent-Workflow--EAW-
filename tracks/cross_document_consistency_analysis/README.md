# Cross Document Consistency Analysis

This generic track asks whether documents describing a system tell a coherent story. It compares evidenced, applicable claims, tests material incompatibility, reasons about authority and downstream impact, and recommends documentary dispositions without changing the corpus or product behavior.

Sequence: ingest ? intake ? source_inventory ? document_model ? consistency_analysis ? conflict_analysis ? impact_analysis ? disposition_analysis ? critical_review ? analysis_package.

Ingest catalogs supplied material; intake fixes the question. Source inventory discovers mapped target roots through SOURCE_DISCOVERY_TARGET_ROOTS. It writes analysis/10_source_manifest.yaml plus provenance/gaps. Discovery does not imply material necessity: only records with required true and availability available propagate through read_sources_from: required_inventory_sources and evidence_manifest. Repository keys and relative paths remain attached to stable IDs and reproducible locators. Infrastructure repositories are excluded. External evidence retains explicit access/provenance limits rather than impersonating local repository paths.

Document/claim registers, comparison matrix/observations, conflict/authority assessment, impact map/narrative, disposition register/recommendations, and critical-review observations are separate outputs. Each nonterminal phase emits a compact investigations/20_handoff.json. The terminal emits three source documents and analysis/70_package_handoff.md. Completion requires only each producer's own outputs; critical review challenges conclusions and preserves limitations without becoming approval.

Finding records preserve current and inherited IDs, meanings, history, provenance, affected documents/claims, evidence locators, materiality, authority reasoning, dependency, rationale and recommended documentary changes. Controlled disposition states are RESOLVED, OPEN, SUPERSEDED, NOT_REQUIRED and TBD. RESOLVED needs evidence that the inconsistency is no longer active; supersession needs an explicit supported relationship. Recency alone never establishes authority. Ambiguous authority remains OPEN/TBD; absent evidence never proves absent behavior.

Delivery independently selects exact DELIVERY_TARGETS keys from runtime candidates. Evidence from two repositories can be delivered to one. The current helper eaw_delivery_persist_selected_file receives source, target, repos_conf, phase_file, scope_file, card_id, selection_file. Three semantic destinations are docs/cross-document-consistency-analysis.md, docs/cross-document-consistency-findings.yaml, and docs/cross-document-consistency-decisions.yaml. Source artifacts are card-local; product copies are self-contained and exclude card identifiers, internal operational paths, phases and lifecycle language. Targets derive only from declared paths and selected roots; an existing scope lock narrows authorization. No direct target write or manual allowlist is permitted. Destination directories must already exist.

ANALYSIS_STATUS, COVERAGE_STATUS, REQUIRED_AVAILABLE_NOT_EXAMINED and PERSISTENCE_STATUS are independent. NOT_PERSISTED is a pre-call state only; final states match the existing helper contract. Byte equality and successful helper persistence are required before PERSISTED. Required delivery completion cannot pass on blocked persistence; the analysis itself remains available and can be incomplete with explicit gaps.

Official cycle from the runtime root: scripts/eaw tracks install; scripts/eaw validate workflow --all; scripts/eaw validate-prompt cross_document_consistency_analysis PHASE v1 for each of the ten phases. Prompt updates use new versions and official validate/apply lifecycle. Phase agents do not operate the workflow CLI.

Run python tracks/cross_document_consistency_analysis/tests/smoke.py for replay-safe, read-only structural checks using PyYAML. --runtime-contracts additionally exercises the real discovery/propagation and single-target persistence helpers in a temporary neutral corpus with teardown; the orchestrator runs this option because it writes outside phase scope. --cases prints the complete neutral A?F cognitive scenarios and required assessment criteria. These are evaluation inputs, never a classifier or prefilled analysis. A?F require an agent to execute the relevant prompts on these cases, produce actual traced outputs and have those outputs reviewed. Passing structural assertions is not cognitive validation. G/H runtime tests exercise helper behavior; I/J inspect structural product hygiene/boundaries and require final artifacts/diff review in governed validation. All A?J evidence must pass before readiness is declared. Historical unrelated global prompt failures remain a separately recorded diagnostic.
